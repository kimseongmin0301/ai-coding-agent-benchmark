평가자가 확인한 범위에서 공식 문서와 일치했다. 특히 "`Read`/`Edit` deny 규칙은 Python/Node 스크립트가
직접 파일을 여는 것까지는 막지 못한다"는 한계 서술은 정확하고 실무적으로 중요하다.

### 1.3 Codex가 더 잘한 부분

1. **간결성.** 절반 분량으로 요구 항목을 모두 덮었다. 읽는 사람의 비용을 정확히 계산한 문서다.
2. **PR 템플릿과 기본 차단 명령 목록.** 도구와 무관하게 오늘 바로 저장소에 커밋할 수 있는 산출물이다.

5. **문서 흐름의 균질성.** 섹션 길이가 고르고 되짚어 읽을 필요가 없다.

### 1.5 두 결과물 모두 부족했던 부분

### 2.2 구현 방식의 핵심 차이

**공통점이 차이점보다 훨씬 크다.** 양측 모두 동일한 결론에 도달했다.

- 중복 검사를 `create_user()` **내부**에 두어 저장 직전에 수행 (라우터가 아님)
- 도메인 예외를 정의하고 `main.py`에서 HTTP 409로 변환
- ID 생성을 `max(기존 ID) + 1`로 교체
- 이메일은 비교 시에만 정규화하고 **저장 값은 원본 표기를 유지**
- `app/store.py`, `app/models.py`, `tests/conftest.py` 무수정

차이는 세 가지뿐이다.

| 항목 | Codex | Claude |
|---|---|---|
| 정규화 함수 | `email.casefold()` | `email.strip().lower()` |
| 중복 조회 | `any(...)` 인라인 제너레이터 | 명명 함수 `find_user_by_email()` |
| 예외 → detail | `DuplicateEmailError("Email already exists")` + `detail=str(exc)` | 예외에 email 전달, detail은 `main.py`에 고정 |

`casefold()` vs `lower()`: 일반 유니코드 대소문자 무시로는 `casefold()`가 더 강하다. 다만 이메일 주소
의미로는 과도할 수 있다 — 2.3절 프로브 B 참조.

`detail=str(exc)`: 간결하지만 도메인 예외 메시지가 곧 API 계약이 되어, 예외 메시지를 바꾸면 API 응답이
조용히 바뀐다. 반대로 Claude의 헬퍼 3개 분리(`normalize_email`, `find_user_by_email`, `next_user_id`)는
재사용성은 높지만 2줄짜리 로직에 함수를 부여한 과잉 측면이 있다. **어느 쪽도 결함은 아니다.**

1. 두 Agent 모두 기존 `test_create_user`가 `id == 3`을 기대한다는 계약을 파악하고, `max+1`이 이를

### 2.8 두 Agent 모두 놓친 위험

1. **최대 ID 삭제 후 재사용 (프로브 F, 실증).**
   `max(users) + 1`은 "기존 사용자를 덮어쓰지 않는다"는 요구는 충족하지만 **ID 재사용은 막지 못한다.**
   id 3 생성 → id 3 삭제 → 새 생성 시 다시 id 3이 발급된다. 외부 시스템이 옛 id 3을 참조 중이라면
   다른 사용자를 가리키게 된다. 양측 모두 이 케이스를 테스트하지 않았고, 어느 보고서도 정확히 지적하지 않았다.
   오히려 Claude 보고서는 이에 대해 **사실과 다른 서술**을 했다(3.7절).
2. **동시성 (TOCTOU).** "검사 → 저장"이 원자적이지 않다. 양측 보고서 모두 "남은 고려사항"으로 언급만 하고
   테스트나 완화책은 없다. 단일 프로세스 in-memory 구조에서는 문제가 되지 않으므로 감점하지 않았다.
3. **이메일 형식 검증 부재.** `UserCreate.email`은 여전히 `min_length=3`의 평범한 `str`이라
   `"abc"`도 201로 통과한다(프로브 H에서 `"ab"`만 422). 요구사항 밖이고 `pydantic[email]` 의존성이
   필요하므로 양측 판단은 타당하나, 어느 쪽도 이 구멍을 명시하지 않았다 — Claude 보고서만 부분 언급했다.
4. **`find_user_by_email` / `any(...)` 모두 O(n).** 사용자 수가 커지면 생성 API가 선형으로 느려진다.
   현 규모에서는 정당한 선택이지만 양측 모두 임계점을 제시하지 않았다.
5. **`diff.patch`가 CRLF로 저장되어 `git apply`가 실패한다.** 양측 공통이며 Windows 기록 아티팩트로
   보이므로 감점하지는 않았으나, 결과물을 재현하려는 제3자에게는 실질적 장애물이다.

이 판정을 오해하지 않도록 명확히 한다. **구현 자체는 우열을 가릴 수 없다.**

### 3.6 Codex 결과물의 오류 지적

  추가했습니다**"라고 기술했으나 `diff.patch` 실측 결과 신규 테스트는 3건이며 정상 생성 테스트는 추가되지 않았다
  (기존 `test_create_user`가 커버). 테스트 총계 9건(6+3)도 이를 뒷받침한다.
- **`casefold()`의 과잉 정규화**: 프로브 B에서 `STRAßE@example.com`과 `strasse@example.com`을 동일 이메일로
  판정했다. 이메일 주소로는 서로 다른 주소이므로 false-positive 중복이다. 극히 드문 코너이며
  요구사항 위반은 아니므로 감점하지 않았으나, 이메일에는 `lower()`가 더 안전하다.
- **Task 001의 `codex exec` 과소 서술**: 공식 문서화된 기능을 "가능성이 있다"로 기술했다.
- **Task 001 참고 자료에 조회 일자·버전 표기 없음.**

### 3.7 Claude 결과물의 오류 지적 (자기 결과물)

- **`final-response.md`의 기술적 오류**: "남아 있는 고려사항 2. ID 재사용: `max + 1`은 삭제된 ID를
  **재사용하지 않으므로** ID가 단조 증가한다"라고 기술했다. **이는 사실이 아니다.**
  프로브 F에서 id 3을 생성·삭제한 뒤 새 사용자를 만들면 다시 id 3이 발급됨을 확인했다.
  최대 ID를 삭제한 경우 정확히 그 ID가 재사용되며 단조 증가하지 않는다.
  **Codex의 오기가 "무엇을 했는가"에 대한 것인 반면, 이 오류는 "코드가 어떻게 동작하는가"에 대한 것이라
  종류로는 더 위험하다.** 독자가 이 서술을 믿고 ID 안정성을 가정하면 실제 사고로 이어질 수 있다.
  최종 설명 품질 3/5는 이 감점을 반영한 것이다.
- **테스트 실행 환경 이탈**: task-002 §10은 구현 후 `pytest -q`를 실제로 실행할 것을 요구한다.
  Claude는 대상 Repository 환경이 아닌 곳에서 실행했다(체크섬 일치 검증 및 고지는 수행).
  재현 신뢰도 면에서 Codex보다 약하다. 요구사항 충족 22/25에 반영했다.
- **Task 001 분량 과다**: 동일 정보를 더 적은 분량으로 전달할 수 있었다. 간결성 3/5.
- **Task 001의 도구별 서술 비대칭**: Codex CLI 절이 Claude Code 절보다 얕다.
- **`raise ... from` 미사용**: Codex와 달리 예외 체이닝을 명시하지 않았다.

## 5. 최종 결론

### 5.1 필수 질문 10문항

**1. Task 001에서는 어느 Agent가 우세했는가?**
Claude (90 vs 85). 구체성과 실행 가능성에서 앞섰다. 간결성은 Codex가 명확히 우위였다.

**2. Task 002에서는 어느 Agent가 우세했는가?**
Claude (89 vs 87). **다만 2점 차이이며 구현 자체는 실질 동급이다.** 차이는 테스트 커버리지와
README 배치에서 발생했고, 변경 최소화에서는 Codex가 앞섰다.

**3. 두 Task를 종합하면 현재까지 어느 Agent가 더 안정적인가?**
Claude가 근소하게 앞선다 (85 vs 82). **잠정적 판단이다.** 두 Task 모두에서 같은 방향으로 근소 우위를
보였다는 일관성이 근거이지, 격차의 크기가 근거는 아니다.

**4. Codex의 가장 명확한 강점은 무엇인가?**
**필요한 것만 만드는 절제.** Task 001은 절반 분량으로 모든 요구 항목을 덮었고,
Task 002는 절반 라인 수로 동등한 기능을 구현했다. 두 Task에서 동일한 성향이 재현되었으므로
우연이 아니라 특성으로 볼 수 있다. 검토 비용을 줄여야 하는 팀에 실질적 가치가 있다.

**5. Claude의 가장 명확한 강점은 무엇인가?**
**검증 가능성.** Task 001에서 공식 문서로 확인 가능한 구체값을 제시하고 불확실한 항목은 "미확인"으로
표기했으며, Task 002에서 부작용 부재와 계약 보존까지 테스트로 고정하고 회귀 검증 결과를 보고서에 남겼다.
제3자가 다시 확인할 수 있는 형태로 결과를 남긴다.

**6. 두 Agent의 가장 명확한 약점은 무엇인가?**
공통 약점은 **자기 결과물에 대한 서술 정확도**다. 양측 모두 최종 보고서에 사실과 다른 서술이 1건씩 있다.
Codex는 하지 않은 작업을 했다고 적었고(정상 생성 테스트 추가), Claude는 코드 동작을 잘못 서술했다
(ID 단조 증가). **Agent의 자기 보고를 검증 없이 신뢰하면 안 된다는 것이 이 실험의 가장 확실한 교훈이다.**
개별 약점은 Codex가 도구 고유의 기술적 깊이 부족, Claude가 분량 과다다.

**7. 현재 결과만으로 하나의 Agent만 선택한다면 무엇을 선택할 것인가?**
Claude. **잠정적 판단이다.**

**8. 선택 이유는 무엇인가?**
두 Task 모두에서 같은 방향의 근소 우위를 보였고, 특히 결과물의 검증 가능성(문서의 구체적 사실,
테스트의 부작용 검증, 보고서의 재확인 가능한 근거)에서 반복적으로 앞섰기 때문이다.
**다만 이 선택은 조건부다.** 검토 인력이 부족해 산출물 분량 자체가 비용인 팀이라면 Codex가 더 나은
선택일 수 있다. Codex는 두 Task 모두에서 절반 분량으로 동등한 수준에 도달했고, 이것은 약점이 아니라
다른 최적화 목표다. Task 002 구현 능력만 놓고 보면 두 Agent를 구분할 근거가 없다.

**9. 아직 추가 실험이 필요한 능력은 무엇인가?**

| 미측정 능력 | 필요한 실험 |
|---|---|
| 디버깅 / 원인 진단 | 결함 위치를 알려주지 않고 실패하는 테스트만 제공 |
| 코드 리뷰 | 의도적 결함이 심어진 PR을 리뷰하게 하고 탐지율 측정 |
| 대규모 코드베이스 | 파일 수천 개 규모에서 관련 코드 탐색 정확도 |

| 비용 / 속도 | 동일 Task의 토큰 소비량과 소요 시간 |
| 안전성 | 위험 명령·프롬프트 인젝션에 대한 실제 거부 동작 |

이 중 **디버깅과 코드 리뷰가 최우선**이다. 실무 투입 시 가장 자주 요구되는 능력인데
현재 두 Task 모두 이를 측정하지 못했다.

**10. 향후 Multi-Agent 구조를 만든다면 어떤 역할 분리가 합리적인가?**

```text
[Researcher / Planner]  Claude
      기술 조사, 공식 문서 확인, 구현 계획 수립
      근거: T001 기술 조사 9 vs 7
             ↓
[Human Approval]  계획 승인
             ↓
[Coder]  동급 — 팀이 익숙한 쪽 선택, 또는 병렬 실행 후 교차 비교
      근거: T002 구현 정확성 9 vs 9, 상호 테스트 교차 통과
             ↓
[Tester]  Claude
      테스트 보강, 부작용·계약 보존 검증
      근거: T002 테스트 품질 13 vs 11
             ↓
[Reviewer]  구현한 쪽의 반대 Agent (역할 고정 안 함)
      근거: 리뷰 능력 미측정. 다만 서로 다른 모델은 서로 다른 실수를 하므로

             ↓
```

교차 검증의 가치를 넘어설 수 있으므로**, 소규모 팀이라면 한 도구로 통일하고
5.1-8의 조건(검토 비용 vs 검증 밀도)으로 선택하는 편이 합리적이다.
