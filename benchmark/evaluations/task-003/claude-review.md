### 2.1 Task 002 기능 유지 — Claude의 명확한 미충족

`task-003.md`는 세 곳에서 Task 002 기능 유지를 요구한다.

```text
§4  "Task 002에서 사용자 생성 안정성 개선이 적용된 baseline을 사용한다."
§6-G "Task 002에서 추가된 이메일 중복 방지와 ID 충돌 방지 로직도 유지한다."
task-003-run.md 최종 검토 체크리스트 "Task 002 기능이 유지되는가"
```

실행 결과는 다음과 같다.

| 프로브 | Codex | Claude |
|---|---|---|
| P11 중복 이메일 `ALICE@example.com`로 POST | **409** `Email already exists` | **201 생성됨** (중복 허용) |
| P12 user 1 삭제 후 신규 생성 | `new_id=3`, **Bob 무사** | `new_id=2`, **Bob이 덮어써짐** |

Claude 구현에는 **실제 데이터 손상 버그가 살아 있다.** user 1을 삭제한 뒤 사용자를 생성하면
`len(users)+1 = 2`가 되어 기존 user 2(Bob)를 덮어쓴다. V5에서 Codex 테스트 3건이 실패한 이유가 이것이다.

**양측 모두 baseline에 Task 002가 없다는 사실을 인지했다.** 대응이 갈렸다.

- **Codex**: `plan.md`의 "수정 예상 파일"에 *"Task 002 기능이 현재 코드에 없으면 이메일 중복 방지와
  안전한 ID 생성도 함께 반영"*을 **조건문 형태로 미리** 적었고, "예상 위험"에도 같은 항목을 넣었다.
  구현에서 최소 범위로 복원했다.
- **Claude**: `plan.md` §0에서 §2와 §4·§6-G의 불일치를 발견해 commit 단위로 추적하고,
  §2를 우선한다고 판단했다. 근거는 (a) §2가 브랜치를 명시한 유일한 실행 지시, (b) 상대 Agent도
  같은 트리에서 시작하므로 비교 가능성 유지, (c) §8의 범위 제한이다. `final-response.md`에도 재기록했다.

**평가자 판단: Codex의 해석이 문서가 기술한 최종 상태를 만든다.**

Claude의 논증은 성실하고 근거도 명확하다. 특히 (b)는 실험 설계 관점에서 타당한 지적이다.
그러나 세 가지 이유로 Codex 쪽을 옳다고 본다.

1. §2는 *어디서 시작할지*를 지정하고 §4·§6-G는 *무엇을 만족해야 하는지*를 지정한다. 층위가 다르므로
   §2를 따랐다는 사실이 §6-G를 면제하지 않는다.
2. Codex도 **동일한 baseline에서 시작했다.** 즉 (b)의 우려는 실제로 발생하지 않았고,
   Task 002 복원은 두 Agent의 출발점을 다르게 만들지 않는다.
3. §8의 금지 항목은 *"기존 Task 002 기능 제거 또는 재설계"*와 *"검색 기능과 관계없는 대규모 리팩터링"*이다.
   Codex가 추가한 것은 총 15줄(service.py) 규모이고 문서가 명시적으로 이름 붙인 두 기능이다.
   "대규모 리팩터링"으로 보기 어렵다.

다만 문서 자체에 모순이 있었던 것은 사실이므로 감점을 -4로 제한했다. 12개 항목 중 1개 미충족이지만,
결과물에 데이터 손상 버그가 남았다는 점을 고려하면 단순 비례 배분(-1.7)보다는 무겁게 보아야 한다.

## 3. 설계 적절성 (Codex 18 / Claude 18) — 동점

### 3.1 핵심 설계 판단이 완전히 일치한다

| 판단 지점 | Codex | Claude |
|---|---|---|
| 검색 로직 위치 | `app/service.py`의 `search_users_by_email()` | 동일 |
| Validation 위치 | `app/main.py` route에서 `HTTPException(400)` | 동일 |
| Response model | `list[UserResponse]` 재사용, `models.py` 무수정 | 동일 |
| 신규 model 추가 | 없음 | 없음 |
| 정렬 규칙 추가 | 없음 (저장 순서 유지) | 없음 |
| `strip()` 등 임의 정책 | 없음 | 없음 |
| Route 순서 | `/users/search`를 `{user_id}` 앞에 선언 | 동일 |

두 Agent가 독립적으로 같은 결론에 도달했다. 특히 **양측 모두 `Query(min_length=2)` 함정을 피했다.**
pydantic 검증에 위임하면 요구된 400이 아니라 422가 반환되는데, 양측 다 명시 검증을 택했다.
이것이 이번 과제에서 가장 중요한 설계 분기점이었고 **둘 다 정확히 통과했다.**

### 3.2 Codex의 설계 특징

- **`_normalize_email()` 공용 helper.** 검색 비교와 Task 002 중복 비교가 같은 정규화 정책을 공유한다.
  정규화 규칙이 한 곳에만 존재한다는 점에서 응집도가 좋다. `plan.md`에서 이 재사용을 미리 의도했다고
  밝혔고 실제 구현이 그대로다.
- `casefold()` 사용. 유니코드 폴딩이 더 공격적이라 P13에서 `STRAßE`가 `strasse`와 매칭된다.
  **검색(부분일치) 용도에서는 재현율이 높아지는 방향이라 결함으로 보지 않는다.**
- `DuplicateEmailError(ValueError)` + `raise ... from exc` 체이닝. 파이썬 관례에 맞다.
- 약점: `detail=str(exc)`로 도메인 예외 메시지를 그대로 API 계약으로 노출한다. 예외 메시지를 바꾸면
  API 응답이 조용히 바뀐다. (Task 002 영역 코드이므로 비중은 작다.)

### 3.3 Claude의 설계 특징

- **`MIN_SEARCH_KEYWORD_LENGTH = 2` 상수**를 두고 detail 문자열을 이 값에서 생성한다.
  Codex는 `len(email) < 2`와 `"...at least 2 characters"`에 숫자 2가 **두 번 하드코딩**되어 있어,
  임계값을 바꾸면 메시지가 낡는다. 실측으로 확인한 차이다.
- **route 위 NOTE 주석**으로 선언 순서 의존성을 코드에 남겼다. Codex는 순서를 지켰지만
  코드에는 이유를 남기지 않았다(`final-response.md`에만 기재).
- 검색 함수에 docstring. "저장 값은 변경하지 않고 비교에만 정규화" 정책을 명시한다.
- `lower()` 사용. 이메일 주소 의미로는 `casefold()`보다 보수적이지만, 검색 용도에서는
  재현율이 낮아지는 방향이다. **우열을 가릴 사안이 아니다.**
- 약점: 정규화 helper가 없어 `keyword.lower()`와 `user["email"].lower()`가 인라인으로 나뉜다.
  현재는 한 함수 안이라 문제없지만 Codex의 공용 helper보다 응집도가 낮다.

### 3.4 종합

Codex는 "정규화 helper 공유"에서, Claude는 "매직넘버 제거 + 순서 의존성 문서화"에서 각각 앞선다.
과도한 추상화는 양측 모두 없다. **18/18 동점이 적절하다.**

### 5.5 기타 확인

2. 매직넘버 `2`가 조건문과 메시지 두 곳에 하드코딩되어 있다. 임계값 변경 시 메시지가 낡는다.
3. 91자 라인 1건.
4. route 순서 의존성을 **코드에 남기지 않았다.** 재배열하면 조용히 깨지고, 그 사실을 지목하는
   전용 테스트도 없다(검색 테스트가 간접 보호할 뿐).
5. `detail=str(exc)`로 도메인 예외 메시지를 API 계약에 결합했다.
6. 요구 테스트 7번(기존 `/users` API)에 대응하는 **전용 신규 테스트가 없다.**
7. README에 route 순서 주의사항이 없다.

**설계 특징** — 최소주의. 기존 구조를 그대로 따르고 공용 helper로 중복을 제거한다.
추상화를 새로 만들지 않으며 필요한 것만 추가한다.

**테스트 특징** — 요구 케이스를 전체 body로 정확히 고정하는 방식. 신규 9종 전부가 baseline에서
실패하는 유효한 회귀 테스트다. 구조적 테스트(route 순서, 파라미터 누락)는 없다.

**계획 수행 특징** — 계획이 실행 지시서에 가깝다. 불확실성을 **조건부 항목**("없으면 함께 반영")으로
미리 흡수해 계획 변경 자체가 발생하지 않게 설계했다. 전 항목이 구현과 일치한다.

### 15.2 우세하다고 판단한 핵심 이유

**요구사항 충족의 완결성 하나다.**

시작했으므로 Claude가 우려한 "출발점 불일치"는 실제로 발생하지 않았고**, Codex가 추가한 코드는
15줄 규모로 §8이 금지한 "대규모 리팩터링"에 해당하지 않는다. 결과물 기준으로 Codex의 해석이 옳다.

- **검토 비용: Codex 우세.** 결과 문서 7 KB vs 35 KB.
- **사용자 개입: 동점.** 양측 모두 추가 질문 0회, 힌트 0회.

> **품질 대비 실행 효율 우세: Codex.**
> 더 높은 품질을 같은 변경량, 더 적은 반복, 더 적은 문서량으로 달성했다.
> 단 시간 지표가 빠진 판정임을 명시한다.

### 15.6 Planner 역할에 대한 새로운 판단

**Task 001–002의 "Claude 근소 우세"에서 "동점"으로 내린다.**

Task 003은 계획 능력을 처음으로 직접 측정한 과제였고, 결과는 **계획의 상세함과 계획의 정확함이
다르다**는 것을 보여줬다. Claude 계획은 12 KB로 대안 비교와 위험 7종을 담았지만 **대전제(baseline
해석)가 어긋나 요구사항 미충족으로 이어졌다.** Codex 계획은 3 KB로 짧지만 불확실성을
조건부 항목으로 흡수해 **계획 변경 없이 완결된 결과**를 만들었다.

계획서의 깊이는 Claude, 계획의 목표 설정 정확도는 Codex. 동점이 적절하다. 확신도 중간.

### 15.7 Coder 역할에 대한 새로운 판단

**Task 002의 "판단 보류(실질 동점)"에서 "Codex 근소 우세"로 조정한다. 확신도는 낮음이다.**

근거는 **구현력 자체가 아니라 완결성**이다. 검색 기능만 보면 두 구현은 여전히 구분되지 않는다
(프로브 13/15 일치, Codex 구현이 Claude 테스트 100% 통과). 그러나 **Codex 결과물만 요구사항
12/12를 충족했고 변경 효율도 높다.**

두 Task 연속으로 "순수 코드 작성 능력의 차이"는 관측되지 않았다. 갈린 것은 매번 **무엇까지 할지에
대한 범위 판단**이었다. 확신도를 낮음으로 두는 이유다.

### 15.8 Tester 역할에 대한 새로운 판단

**Task 002의 "Claude 우세"에서 "동점"으로 내린다.**

Task 003에서 두 방향이 뚜렷이 갈렸다.

- **Codex**: 단언 엄격도. 다건 검색에서 두 사용자의 **전체 dict**를 단언한다(Claude는 id 목록만).
  신규 9종 **전부**가 baseline에서 실패하는 유효한 회귀 테스트다.
- **Claude**: 커버리지 폭. 기존 API 전용 테스트, route 구조 테스트, 파라미터 누락 테스트를 갖췄고
  순서 파괴 시 더 많이(8 vs 6) 탐지한다.

평가 문서 §9가 "여러 사용자 반환 내용을 정확히 검증하는가"와 "기존 /users API 유지"를 **모두**
요구하는데 각자 하나씩만 충족했다. 동점이 적절하다. 확신도 중간.
